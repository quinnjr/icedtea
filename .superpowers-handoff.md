## H1 (blocks F77) — `font-width` cannot be told from unset

`ui/src/text.rs::TextStyle::from_computed` has to know whether `font-width`
was *specified*, not just what it computed to. GTK 4.22 registers
`font-width` and `font-stretch` as two rows over one grammar, and the L4
name is meant to win only where it is set; today `stretch_percent(FontWidth)
== 100.0` is the only "unset" test there is, so an explicit
`font-width: normal` loses to `font-stretch: ultra-expanded`.

Either of these closes it:

```rust
// ui/src/css/computed.rs
impl ComputedStyle {
    /// Whether a declaration for `prop` won the cascade for this element,
    /// as opposed to the value coming from the registry initial or from
    /// inheritance.
    #[must_use]
    pub fn is_specified(&self, prop: Prop) -> bool;
}
```

or, better, make the cascade treat `font-width` and `font-stretch` as
aliases of one another so the later declaration simply wins, and have both
`raw(Prop::FontWidth)` and `raw(Prop::FontStretch)` report it.

## H2 (perf) — resolve a gradient's stops once, not per pixel

`Gradient::color_at` (`ui/src/css/value/image.rs:666`) allocates two `Vec`s
per call — `stop_positions` and the resolved colours — and
`paint::background::paint_gradient` calls it *once per pixel*. Requested:

```rust
// ui/src/css/value/image.rs
/// Every stop resolved once, for a caller that samples one gradient at many
/// points.
pub struct ResolvedStops {
    pub positions: Vec<f32>,
    pub colors: Vec<Rgba>,
}

impl Gradient {
    #[must_use]
    pub fn resolve_stops(&self, ctx: &ColorCtx<'_>, len_ctx: &LengthCtx) -> ResolvedStops;

    /// The colour at gradient-line parameter `t`, against already-resolved
    /// stops. `color_at` becomes `self.color_at_resolved(t, &self.resolve_stops(..))`.
    #[must_use]
    pub fn color_at_resolved(&self, t: f32, stops: &ResolvedStops) -> Rgba;
}
```

Semantics must be identical to today's `color_at`, byte for byte, or the M1
pixel gate moves.

## H3 (correctness, pairs with wave B's F76 patch) — relative font weights

`FontWeight::Bolder` / `FontWeight::Lighter` reach `TextStyle::from_computed`
unresolved; nothing in the crate resolves them against the parent's computed
weight. Wave B has mapped them to CSS Fonts 4 §2.2's values *against a 400
parent* (700 / 100) so `bolder` at least stops producing a lighter face than
its bold parent, but the real fix is in `computed.rs`'s inheritance pass:
resolve `bolder`/`lighter` against `parent.font_weight` into
`FontWeight::Absolute` at computed time. Wave B's arm then becomes dead and
harmless.

## H4 (belt-and-braces, pairs with wave B's F78 patch) — `line-height: <percentage>`

`computed.rs:736` leaves a percentage `line-height` unresolved even though
its basis (the element's own `font-size`) is in hand at line 604. Wave B now
resolves it in `TextStyle::line_height_px`, so nothing is broken today, but
per contract §5's resolution order it should be absolute by computed time.
