## calc — commit `a9249db`

### F22 `ui/src/css/value/calc.rs` `CalcNode::eval`, `Clamp` arm — VERIFIED-FIXED
Real. `clamp(MIN, VAL, MAX)` is `max(MIN, min(VAL, MAX))` in CSS Values 4; the code did
`min(max(VAL, MIN), MAX)`. The two agree whenever MIN <= MAX and disagree when inverted.
RED: `clamp(10px, 5px, 2px)` gave `Some(2.0)`, expected `Some(10.0)`.
GREEN + test `calc::review_tests::an_inverted_clamp_resolves_to_its_minimum_not_its_maximum`,
which also pins the three non-inverted cases so the reorder cannot regress them.

### F23 `calc.rs` `combine` — VERIFIED-FIXED
Real. A bare `<number>` adopted the other operand's unit. RED: `calc(4px + 2)` gave
`Some(6.0)`, expected `None`. The `(Number, other)` arms were *only* reachable for the
invalid mixed case — a genuine `calc(2 + 3)` matches on discriminant — so removing them
loses nothing. GREEN + test `a_bare_number_never_inherits_the_other_operands_unit`.

### F24 `calc.rs` `parse_product` — VERIFIED-FIXED
Real. `resolve_number` flattens a `<percentage>` to its fraction, so `*`/`/` accepted one
as a scalar. RED: `calc(2 * 50%)` gave `None` (a bare number, invalid as a length) against
a 200px basis where `calc(50% * 2)` gave 200. Fixed with a structural type test
(`CalcNode::is_number_typed`, new) rather than an evaluation, which also makes
multiplication commutative again and rejects `calc(3px * 50%)`.
GREEN + test `a_percentage_is_never_demoted_to_a_bare_multiplier`.

### Priority item: unbounded calc chain — VERIFIED-FIXED
Real. `MAX_TERMS = 64` caps `parse_sum`/`parse_product`. The left-deep AST made an
n-term chain n frames deep in `eval`, in the derived `PartialEq` and in `Rc`'s drop
glue, and O(n^2) to parse because every `*` re-evaluated its left operand.
RED: a 73-term chain parsed to `Some(73.0)` instead of `None`.
Test `an_unbounded_operand_chain_is_refused_rather_than_overflowing_the_stack`.
*Honest limitation:* the test demonstrates the cap, not an actual overflow — a chain long
enough to overflow would abort the test process rather than fail it.
