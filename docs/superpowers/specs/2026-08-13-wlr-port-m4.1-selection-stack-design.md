# icedtea-wm — wlr port Milestone 4.1: Selection stack

Date: 2026-08-13

## Addendum (execution outcome)

Decision 2's acceptance policy proved correct but for a different reason than
written: wlroots itself validates the `set_selection` grant serial before
emitting `request_set_selection`, so the crate's unconditional accept only ever
sees requests from a client that holds a valid input serial — which, since only
the focused client receives input events, *is* the focus gate. A client with no
serial (an unfocused one, or any client on a seat with no keyboard) is rejected
by wlroots before the handler runs.

That validation surfaced a headless-testing gap: the headless seat has no input
device, so no client can obtain a serial, so `wl_data_device.set_selection`
(success criterion 1's copy side) could not be exercised. Rather than weaken the
test, M4.1 grew a real, generally-useful protocol: **virtual keyboard**
(`Runtime::create_virtual_keyboard_manager`, published in wlr **0.20.15**), so
the harness injects a keyboard, the seat gains keyboard capability, and a focused
client receives the `wl_keyboard.enter` serial `set_selection` needs. Building it
also exposed and fixed a latent `InputDevice` drop-order use-after-free in the
`wlr` crate (also 0.20.15). Two `wlr` releases shipped for M4.1: **0.20.14**
(selection managers + seat request wiring) and **0.20.15** (virtual keyboard +
the UAF fix). All six success criteria are met; the copy side is proven with an
injected virtual keyboard rather than the "automated-only, no input" assumption
the risks section anticipated.

## Overview

Milestone 4 ("interop essentials") is decomposed into six dependency-ordered
sub-milestones, each its own spec → plan → SDD → merge cycle:

| Sub | Milestone | Depends on |
|-----|-----------|-----------|
| **M4.1** | Selection stack — `wl_data_device` clipboard + primary-selection + `zwlr_data_control` global | — |
| M4.2 | Drag-and-drop (`wl_data_device` DnD) | M4.1 |
| M4.3 | Screencopy (`wlr_screencopy_manager_v1`) | — |
| M4.4 | Session lock + idle (`ext-session-lock-v1`, `idle-notify`/`idle-inhibit`) | — |
| M4.5 | Pointer constraints + relative pointer | — |
| M4.6 | Clipboard daemon (`wlr-data-control` client) + minimal GTK4 shell popover | M4.1 |

This document specifies **M4.1 only**.

M4.1 makes copy/paste work between Wayland clients. Today the compositor
advertises four globals (`xdg_shell`, `xdg_decoration`, `layer_shell`, `seat`)
and creates `wlr_data_device_manager` inside `create_seat`, but exposes no
primary-selection manager, no data-control manager, and no safe surface over
the seat's selection-request events — so a client can bind `wl_data_device`
but a clipboard round-trip between two clients is unverified and
primary/middle-click paste and clipboard-manager access are impossible.

## Decisions of record

1. **Scope is clipboard + primary + data-control global only.** Regular
   selection (`wl_data_device` `set_selection`/offers), primary selection
   (`zwp_primary_selection_v1`), and exposure of the
   `zwlr_data_control_manager_v1` global. Drag-and-drop is **M4.2**, not here.
2. **Acceptance policy: the `wlr` crate auto-accepts a selection request from
   the keyboard-focused client**, validating the wlroots-supplied serial/focus
   internally, and calls `wlr_seat_set_selection` /
   `wlr_seat_set_primary_selection`. The compositor gets **no new handler
   surface** for selection in M4.1. No veto hook (YAGNI — programmatic access
   is what data-control provides).
3. **data-control is "global exposed + read/write tested" here.** The
   `zwlr_data_control_manager_v1` global is created and wired to the seat's
   selection (wlroots does this automatically once the manager exists); a
   data-control *client* reads/sets the selection in the wire tests. The
   actual `icedtea-clipboard` daemon that consumes it is **M4.6**.
4. **wlroots implements the server side; the `wlr` crate wraps existing
   managers.** No protocol is implemented from scratch. The `wlr-sys` bindgen
   allowlist is wholesale (`wlr_.*` / `WLR_.*`), so the FFI is already
   generated provided the relevant wlroots headers are in the wrapper set — a
   header-list check is a plan task, not new binding work. A `wlr-sys`
   republish is expected to be **unnecessary**; if a header is missing it
   becomes a scoped `wlr-sys` addition + republish, surfaced in the plan.
5. **Split-phase publish→consume, as in M1–M3.** One additive `wlr` `0.20.x`
   release carries the M4.1 additions; the API-review verdict is held by the
   controller before the mechanical publish; the compositor then bumps and
   consumes. No existing published item changes name/signature/semantics.
6. **Validation is automated-only.** The M2 wire-level client harness is
   extended with real two-client clipboard/primary round-trips and a
   data-control read. No manual VM checklist item gates M4.1.
7. **Execution via Subagent-Driven Development.** Per-task
   implement→review→fix-loop, ledger under
   `.superpowers/sdd/2026-08-13-wlr-port-m4.1/`, final whole-branch review,
   merge window presented (never auto-merged).

## Architecture: where the work lives

wlroots owns the protocol machinery. Once `wlr_data_device_manager`,
`wlr_primary_selection_v1_device_manager`, and `wlr_data_control_manager_v1`
exist, and the seat has a keyboard-focused client, wlroots auto-delivers the
current selection's `wl_data_offer` (and primary/data-control equivalents) to
that client and handles the offer/receive fd plumbing. The compositor already
drives keyboard focus through `sync_seat_focus` (`state.rs`), so
selection-follows-focus is already in place structurally.

The only gaps are (a) two manager globals are never created, and (b) the
seat's `request_set_selection` / `request_set_primary_selection` events — a
focused client asking to *become* the clipboard owner — must be answered by
calling back into wlroots. Both are closed in the `wlr` crate; the compositor
only creates the globals at boot.

### `wlr` crate additions (one additive `0.20.x` publish)

- `Runtime::create_primary_selection_manager(&Display) -> Result<()>` —
  creates `wlr_primary_selection_v1_device_manager` (mirrors the existing
  `create_xdg_decoration_manager` shape).
- `Runtime::create_data_control_manager(&Display) -> Result<()>` — creates
  `wlr_data_control_manager_v1`.
- Internal seat wiring: listen for `request_set_selection` and
  `request_set_primary_selection`; validate the request originates from the
  seat's focused client via the wlroots-supplied serial; on success call
  `wlr_seat_set_selection` / `wlr_seat_set_primary_selection`. This is
  crate-internal — no new public handler trait.
- Confirm the `wl_data_device_manager` created in `create_seat` has its
  selection request event handled the same way (today it may be created but
  its request event dropped); consolidate both regular and primary selection
  through one internal path.
- Test-support surface: `Runtime::selection_mime_types() -> Vec<String>` (and
  the primary equivalent) so a wire test can assert server-side selection
  state directly, plus whatever minimal accessor the crate's own unit tests
  need for the serial-validation logic. Additive; `for_test`-style gating
  consistent with `KeyEvent::for_test`.

### Compositor additions

- `compositor/src/lib.rs`: call `create_primary_selection_manager` and
  `create_data_control_manager` at boot, alongside the existing
  `create_xdg_shell` / `create_xdg_decoration_manager` / `create_layer_shell`
  calls, with the same error handling (log-and-continue vs hard-fail matched
  to the existing convention).
- `state.rs`: expected near-zero change. Selection-follows-keyboard-focus
  already works through `sync_seat_focus`; this is verified, not built. Any
  change is limited to confirming the focus path does not need to re-assert
  selection on focus change (wlroots handles it).

## Selection acceptance policy

A `set_selection` request carries the serial of the input event the client
believes authorized it. The crate accepts the request iff the requesting
client currently holds the seat's keyboard focus (the wlroots
`request_set_selection` event exposes the client/serial for this check); it
then calls `wlr_seat_set_selection`. A request from a non-focused client is
ignored. Primary selection follows the identical rule. This is the standard
wlroots-compositor behavior (sway/tinywl accept from the focused client) and
requires no compositor participation.

## Testing (automated-only)

- **Wire-level (extend `compositor/tests/client_protocol.rs` + `support/`):**
  - *Clipboard round-trip:* client A binds `wl_data_device`, offers
    `text/plain;charset=utf-8`, calls `set_selection`; client B is given
    keyboard focus, receives the `wl_data_offer`, calls `receive()` on the
    advertised mime, and the harness asserts the bytes read from the fd equal
    what A wrote.
  - *Primary round-trip:* same shape over `zwp_primary_selection_v1`.
  - *data-control read:* a `zwlr_data_control_manager_v1` client, after A sets
    the clipboard, receives the data-control offer and reads the same bytes —
    proving the global is live and seat-wired.
  - *Focus gating (negative):* a client without keyboard focus attempting
    `set_selection` does not become the selection owner.
- **`wlr` crate unit tests:** serial/focus-validation accept/reject logic,
  deletion-verified (must fail if the focus check is removed).
- **Gates:** `cargo test --workspace` and
  `cargo clippy --all-targets -- -D warnings` in the compositor;
  `cargo test -p wlr`, clippy, and `RUSTDOCFLAGS="-D warnings" cargo doc
  --no-deps` in wlroots-sys — all green on the freeze commit before publish.

## Success criteria

1. Two independent Wayland clients exchange a `text/plain` clipboard payload
   through the compositor, asserted at the byte level by an automated test.
2. The primary-selection round-trip passes the same byte-level assertion.
3. A `zwlr_data_control_manager_v1` client reads the current selection —
   proving the daemon (M4.6) will have a live global to attach to.
4. A non-focused client cannot hijack the selection (negative test passes).
5. The `wlr` additions are semver-additive and published as one `0.20.x`
   release; the compositor consumes the published crate (no path/git dep).
6. All gates green in both repos; final whole-branch review clean or with
   findings resolved; merge window presented.

## Out of scope (explicit)

- **Drag-and-drop** — M4.2 (data-source/offer negotiation, drag-icon scene
  node, drop/finish).
- **Clipboard daemon and any UI** — M4.6 (`icedtea-clipboard` client +
  minimal GTK4 shell popover).
- **A compositor selection-veto handler** — no consumer; not built.
- **Persistence, image/rich payloads, multi-seat** — daemon-era concerns
  (M4.6 and beyond).
- **Night light** — not interop; deferred out of M4 entirely.

## Risks

- **Missing wlroots header in the `wlr-sys` wrapper set** for
  primary-selection or data-control. Mitigation: a plan task confirms the
  headers are enabled before any `wlr` wrapping; if absent, a scoped `wlr-sys`
  header addition + republish precedes the `wlr` release (surfaced, not
  hidden).
- **Selection-follows-focus assumption.** If wlroots does *not* auto-reassert
  the selection to a newly focused client in this version, the compositor must
  nudge it on focus change. Mitigation: the focus-gating and round-trip tests
  will expose this; the fix is a localized `sync_seat_focus` addition, already
  anticipated.
- **Harness fd/receive plumbing.** The M2 harness found a real wlroots
  global-array race (worked around via a boot mutex); the selection tests add
  fd-passing, a new harness capability. Mitigation: budget a harness-support
  task separate from the protocol tasks.
