# icedtea-wm — wlr port Milestone 4.6: Clipboard daemon + minimal GTK4 shell

Date: 2026-08-13

## Overview

M4.6 is the shell sub-milestone of M4 (interop essentials). It builds the
project's first user-facing shell — a GTK4 layer-shell panel — plus the
`icedtea-clipboard` daemon that M4.1's `zwlr_data_control` global exists to
serve. It depends only on M4.1 (the data-control global) and the compositor's
existing `org.icedtea.WM` D-Bus service; it needs no new compositor work.

Three components, executed as three reviewable phases:

1. **`contract` extension** — the shared clipboard IPC vocabulary.
2. **`icedtea-clipboard`** — a headless `wlr-data-control` daemon with history,
   serving `org.icedtea.Clipboard`.
3. **`icedtea-shell`** — a GTK4 layer-shell panel: a window/workspace taskbar
   driven by `org.icedtea.WM`, and a clipboard popover driven by
   `org.icedtea.Clipboard`.

The workspace today is `contract`, `config`, `compositor`. M4.6 adds
`clipboard` and `shell` crates. This is the first GTK4 code in the repo.

## Decisions of record

1. **Separate daemon + shell**, not one merged process. `icedtea-clipboard`
   owns the data-control Wayland connection and the history; `icedtea-shell`
   is a D-Bus client that renders the popover. Matches the pre-port design's
   crash-isolation model (klipper/copyq): a fault in clipboard capture never
   takes the shell down, and each has its own `systemd` unit.
2. **zbus for all D-Bus**, on both sides, reusing the `contract` crate's
   types. The compositor already serves `org.icedtea.WM` via zbus; the daemon
   serves `org.icedtea.Clipboard` via zbus; the shell is a zbus *client* of
   both. In the GTK process, zbus runs on a worker and marshals updates to the
   GTK main thread over a **glib channel** — the shell's GTK code only ever
   touches widgets on the main thread.
3. **Full scope: taskbar + clipboard popover.** The shell renders both the
   window/workspace taskbar and the clipboard history popover in this pass.
4. **Automated validation, including the GTK UI.** The bar stays automated.
   The daemon is tested by pure reducer unit tests plus a headless integration
   test against the M4.1 compositor harness. The shell is tested by pure model
   reducers plus GTK integration tests that run the real shell against the
   harness compositor (which is a live headless Wayland display), introspect
   the GTK widget tree, and simulate clicks — asserting both widget state and
   the compositor-side effect. See Testing.
5. **Memory-only history in v1.** Bounded count + per-entry size budget,
   configurable. No redb persistence, no cross-reboot history, no image
   downscaling worker in v1 (text + uri-list mimes only; images deferred).
6. **`gtk4-layer-shell` for the panel.** The shell maps a `zwlr_layer_shell_v1`
   surface via the `gtk4-layer-shell` binding — the same global the compositor
   has advertised since M2.
7. **Execution via Subagent-Driven Development or inline (user's choice at
   plan handoff), phased**: daemon → shell taskbar → clipboard popover, each a
   reviewable increment. Merge window presented, never auto-merged.

## Architecture

```
 ┌────────────────┐   org.icedtea.WM (zbus)    ┌──────────────────────────┐
 │  compositor    │◀──────────────────────────▶│  icedtea-shell (GTK4)     │
 │  (org.icedtea  │   signals + commands       │   ├ taskbar (WM model)    │
 │   .WM)         │                            │   └ clipboard popover     │
 │  + data-control│                            └──────────▲───────────────┘
 │    global      │                                       │ org.icedtea.Clipboard (zbus)
 └───────▲────────┘                                       │
         │ zwlr_data_control (wayland)          ┌──────────┴───────────────┐
         └─────────────────────────────────────│  icedtea-clipboard        │
                                                │   ├ manager (data-control)│
                                                │   └ history (pure)        │
                                                └──────────────────────────┘
```

Both the daemon and the shell connect to the *same* Wayland compositor: the
daemon as a `zwlr_data_control` client, the shell as a `gtk4-layer-shell`
client. Both are also D-Bus clients/servers on the session bus.

## Component 1: `contract` extension

Add to `contract/src` (a new `clipboard` module, re-exported):

```rust
pub const CLIP_BUS_NAME: &str = "org.icedtea.Clipboard";
pub const CLIP_PATH: &str = "/org/icedtea/Clipboard";

#[derive(Clone, Debug, PartialEq, Eq, Serialize, Deserialize, Type)]
pub enum ClipKind { Text, Uris, Image }

#[derive(Clone, Debug, PartialEq, Eq, Serialize, Deserialize, Type)]
pub struct ClipEntry {
    pub id: u64,           // monotonic, stable for the entry's lifetime
    pub kind: ClipKind,
    pub preview: String,   // short human-readable label (truncated text / count)
    pub mime: String,      // the primary mime the entry was captured under
    pub pinned: bool,
    pub source_app: Option<String>, // best-effort, may be None
}
```

The wire signature of `ClipEntry` is locked by a `contract` unit test, exactly
as `WindowInfo`/`WindowUpdate` already are, so a field reorder that would break
the daemon↔shell ABI fails at test time.

## Component 2: `icedtea-clipboard` daemon

Crate layout:

```
clipboard/
├─ Cargo.toml            (bin; deps: wayland-client, wayland-protocols-wlr,
│                         zbus, crossbeam-channel, icedtea-contract, rustix)
├─ src/
│  ├─ main.rs            boot: wayland connect + data-control device; zbus
│  │                     serve org.icedtea.Clipboard; run the two loops
│  ├─ manager.rs         zwlr_data_control client: capture + re-paste
│  ├─ history.rs         pure bounded/deduping history reducer
│  └─ service.rs         zbus interface impl
systemd/icedtea-clipboard.service
```

- **`history.rs` (pure, unit-tested).**
  ```rust
  pub struct History { entries: VecDeque<ClipEntry>, max: usize, budget: usize }
  impl History {
      pub fn push(&mut self, kind: ClipKind, mime: String, bytes: &[u8],
                  source_app: Option<String>) -> Change; // dedupe head; drop over budget
      pub fn pin(&mut self, id: u64, on: bool) -> Change;
      pub fn remove(&mut self, id: u64) -> Change;
      pub fn clear(&mut self) -> Change;      // keeps pinned
      pub fn snapshot(&self) -> Vec<ClipEntry>; // pinned first, then MRU
      pub fn bytes_for(&self, id: u64) -> Option<(String, Vec<u8>)>; // (mime, payload)
  }
  ```
  `Change` is `Changed | Unchanged` so the service only emits `history_changed`
  when the model actually moved. Pins survive `clear`. Newest capture that
  equals the current head is a no-op (dedupe), matching every clipboard
  manager's behavior.

- **`manager.rs` (data-control client).** The production version of M4.1's
  test harness data-control code. On the device's `selection` event: read the
  offered mimes, `receive()` the best supported one (`text/plain;charset=utf-8`,
  then `text/plain`, then `text/uri-list`) over a pipe, and `history.push`. On
  a `service` `Activate(id)` command: look up `bytes_for(id)`, create a
  `zwlr_data_control_source_v1`, `offer` the mime, `set_selection(source)`, and
  answer `send` with the stored bytes. Its own selections must not re-enter
  history (guard by tracking the source it set).

- **`service.rs` (zbus `org.icedtea.Clipboard`).**
  ```
  fn get_history(&self) -> Vec<ClipEntry>
  fn activate(&self, id: u64)      // re-paste: make id the current selection
  fn pin(&self, id: u64, on: bool)
  fn remove(&self, id: u64)
  fn clear(&self)
  #[signal] fn history_changed(...)  // emitted on any Change
  ```

- **Threading (mirrors the compositor's `dbus.rs`).** The Wayland event loop
  runs on the main thread. zbus runs on its own connection/executor. Service
  method calls push commands (`Activate`/`Pin`/`Remove`/`Clear`) onto a
  channel the Wayland thread drains (woken by a self-pipe fd source, exactly
  as the compositor wakes its command loop); the Wayland thread pushes history
  `Change`s back for the emitter to signal. No shared mutable state across
  threads — message passing only.

## Component 3: `icedtea-shell` (GTK4)

Crate layout:

```
shell/
├─ Cargo.toml            (bin; deps: gtk4, gtk4-layer-shell, zbus, glib,
│                         crossbeam-channel, icedtea-contract)
├─ src/
│  ├─ main.rs            GtkApplication; build the layer-shell panel + UI
│  ├─ wm_client.rs       zbus client for org.icedtea.WM (worker → glib channel)
│  ├─ clip_client.rs     zbus client for org.icedtea.Clipboard
│  ├─ taskbar.rs         pure taskbar model + GTK rendering
│  └─ clipboard.rs       pure history-list model + GTK popover
├─ style.css             embedded via include_str!
systemd/icedtea-shell.service
```

- **Panel.** A `gtk4-layer-shell` surface anchored to one edge (bottom by
  default), with an exclusive zone equal to its height, keyboard-interactivity
  `OnDemand`. Layout: a horizontal bar with the workspace indicator, the window
  button list, and a clipboard button that toggles the popover.

- **`taskbar.rs`.** A **pure** `TaskbarModel` folded from `org.icedtea.WM`:
  `get_state()` seeds it; `WindowOpened`/`Closed`/`Updated` and
  `WorkspaceSet`/`List` mutate it. The model is a plain data structure
  (`Vec<WindowInfo>` + workspace state) with a reducer, unit-tested with no GTK.
  A thin render function diffs the model into the `GtkBox` of window buttons
  and the workspace indicator. Clicking a window button calls
  `focus_window(id)`; a middle-click or an ✕ overlay calls `close_window(id)`;
  clicking a workspace calls `set_workspace(id)`.

- **`clipboard.rs`.** A **pure** `ClipboardModel` (the `Vec<ClipEntry>` from
  `get_history` + `history_changed`), rendered as rows in a `GtkPopover`
  `ListBox`. Row click → `activate(id)`; a pin toggle → `pin(id, on)`; a clear
  button → `clear()`.

- **D-Bus bridge.** `wm_client`/`clip_client` run a zbus connection on a worker
  thread, translate signals/replies into an enum, and `send` it over a
  `glib` main-context channel; the GTK main thread receives and applies it to
  the model, then re-renders. Commands (focus/activate/…) go the other way as
  zbus calls issued from the worker. The GTK thread never blocks on D-Bus.

## Testing

**Automated, in both crates.** Native GTK/Wayland deps are available on the
target (Arch); CI runs against the M4.1 headless compositor harness, which is
a real Wayland display.

- **Daemon — `history.rs`**: pure unit tests — dedupe-on-repeat, pin survives
  clear, budget eviction, MRU ordering, `Change` accounting.
- **Daemon — integration** (`clipboard/tests`, reusing the M4.1 harness
  patterns): boot the harness compositor; run the daemon against it; a test
  `wl_data_device` client (with the injected virtual keyboard for the serial)
  copies text → assert it appears via the daemon's `get_history`; call
  `activate(id)` → a second client reads the selection and gets those bytes.
- **Shell — pure models**: `TaskbarModel` and `ClipboardModel` reducers
  unit-tested against synthesized `org.icedtea.WM` / `org.icedtea.Clipboard`
  event sequences, no GTK.
- **Shell — GTK integration** (`shell/tests`): `gtk::init()` against the
  harness compositor's socket (`WAYLAND_DISPLAY`), build the real panel, then:
  - drive WM state (map real windows via harness test clients, or feed the
    worker channel directly) and **introspect the widget tree** — assert the
    window-button count and labels match, and the workspace indicator tracks;
  - **simulate interaction** — `button.emit_clicked()` on a window button and
    assert the compositor receives `Focus`/`Close` (observed on the harness
    event/command channel); open the clipboard popover and assert its rows
    match `get_history`, click a row and assert `activate` was called;
  - assert the panel actually maps as a layer surface (the harness compositor's
    model shows a layer surface, via the existing `LayerPanelClient`-style
    observation on the compositor side).
- **Gates:** `cargo test --workspace`, `cargo clippy --all-targets -- -D
  warnings`. GTK tests that require a display are guarded to run against the
  harness socket, not a developer's live session.

## Success criteria

1. `icedtea-clipboard` captures a clipboard copy into a bounded, deduping
   history and re-pastes a selected entry, proven by an automated
   compositor-harness integration test.
2. `org.icedtea.Clipboard` exposes get/activate/pin/remove/clear +
   `history_changed`, with a locked wire signature for `ClipEntry`.
3. `icedtea-shell` maps a layer-shell panel and renders the live window list +
   workspace indicator from `org.icedtea.WM`, with click-to-focus, close, and
   workspace switching — asserted by GTK widget-tree introspection +
   simulated clicks + compositor-side effect.
4. The shell's clipboard popover renders `org.icedtea.Clipboard` history and
   activates/pins/clears entries — asserted the same way.
5. Two `systemd` units start daemon and shell as part of the graphical
   session, each `Restart=always`, the shell ordered after the daemon.
6. All gates green; the full validation bar is automated (no manual step
   gates the milestone).

## Out of scope (explicit)

- Clock/volume/network applets (the separate pre-port shell-applets spec).
- Image/rich clipboard payloads and downscaling; uri-list is captured, images
  deferred to a v2.
- Persistent (cross-reboot) history; redb-backed clipboard.
- Night light (not interop; deferred out of M4 entirely).
- Multi-monitor panel-per-output; v1 is a single panel on the primary output.
- Theming/config UI; the shell reads the compositor's appearance palette but
  exposes no settings surface.

## Risks

- **GTK-in-CI**: `gtk::init()` needs a Wayland display; the harness compositor
  provides one, but GTK/GDK may need env coaxing (`GDK_BACKEND=wayland`,
  `GSK_RENDERER=cairo` to avoid a GPU requirement). Mitigation: a
  `shell/tests/support` that boots the harness, sets the env, and guards the
  GTK tests; if a GTK test proves genuinely non-hermetic in CI it is marked
  `#[ignore]` with a logged reason rather than silently dropped.
- **zwlr_data_control availability**: satisfied by M4.1 (the global is created
  at compositor boot and covered by M4.1's data-control tests).
- **Daemon self-capture loop**: re-pasting sets a selection the daemon then
  observes; the source-tracking guard must break the loop. Covered by an
  explicit integration test (activate must not duplicate the head entry).
- **glib/zbus thread discipline**: touching a GTK widget off the main thread
  aborts. The design confines all widget access to the main thread and all
  D-Bus to the worker, bridged only by the glib channel; a review checklist
  item verifies no widget handle crosses the channel.

## Execution

New crates `clipboard/` and `shell/` added to the workspace `members`. Branch
`wlr-m4.6` off `develop`. Phased: (1) contract + daemon, (2) shell taskbar,
(3) clipboard popover. Per-phase review; final whole-branch review; merge
window presented for the user's go/no-go — never auto-merged. No `wlr`-crate
or compositor change is anticipated; if one proves necessary it follows the
established split-phase publish discipline.
