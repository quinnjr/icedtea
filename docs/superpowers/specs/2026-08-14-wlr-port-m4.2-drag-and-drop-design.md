# icedtea-wm — wlr port Milestone 4.2: Drag-and-drop

Date: 2026-08-14

## Overview

M4.2 adds pointer- and touch-driven drag-and-drop between Wayland clients,
building directly on the `wl_data_device` machinery M4.1 landed. wlroots
implements the drag state machine (offer → enter → motion → drop, and the
source→destination data transfer); the `wlr` crate wires the seat's
`request_start_drag`/`start_drag` events and renders the drag-icon scene node,
and the compositor creates the globals at boot. Testing needs pointer (and
touch) input the headless harness cannot otherwise produce, so this milestone
also lands a **virtual-pointer** protocol and a test-only touch injector — the
input side of what makes an automated drag reproducible, exactly as M4.1's
virtual keyboard did for `set_selection`.

## Decisions of record

1. **Scope: pointer AND touch drag-and-drop.** `wl_data_device` DnD driven by
   both a pointer grab (`wlr_seat_start_pointer_drag`) and a touch grab
   (`wlr_seat_start_touch_drag`). Tablet/pen DnD is out of scope.
2. **The `wlr` crate wraps wlroots' drag machinery.** No protocol implemented
   from scratch: wire `request_start_drag` (validate the grab serial, then
   `wlr_seat_start_pointer_drag`/`start_touch_drag`) and `start_drag` (create a
   `wlr_scene_drag_icon` node that follows the input). wlroots owns the rest.
3. **Grab-serial validation.** A `request_start_drag` is honored only when its
   serial is one wlroots recorded for the requesting client (a real pointer
   button / touch down) — the same "wlroots gates on a valid grant serial"
   property M4.1 relied on. This is also the focus/authenticity gate.
4. **Testing is automated, via injected input.** Land
   `Runtime::create_virtual_pointer_manager` (`zwp_virtual_pointer_manager_v1`)
   + `new_virtual_pointer` wiring so the harness injects pointer motion/button
   and mints the pointer grab serial. Touch has **no** standard virtual-input
   protocol, so add a **test-only** `wlr`-crate touch injector
   (`inject_touch_*`, gated like `KeyEvent::for_test`) to drive a touch drag.
5. **Split-phase publish→consume, as in M1–M4.1.** One additive `wlr`
   `0.20.x` release (**0.20.16**) carries the DnD wiring + virtual-pointer +
   touch injector; the API-review verdict is held before the mechanical
   publish; the compositor then bumps and consumes. Additive-only within
   0.20.x.
6. **Execution: inline or SDD (user's choice at plan handoff).** Per-task
   review, final whole-branch review, merge window presented — never
   auto-merged.

## Architecture

wlroots owns the drag state machine. When a client requests a drag
(`wl_data_device.start_drag` with a serial), wlroots emits the seat's
`request_start_drag` event; the compositor validates and calls
`wlr_seat_start_pointer_drag`/`start_touch_drag`; wlroots then emits `start_drag`
(carrying the `wlr_drag`), drives the destination client's
`wl_data_device.enter`/`motion`/`drop`, and moves the bytes source→dest. The
only compositor-visible gaps: the two seat events must be wired, and the drag
icon needs a scene node so it is visible following the input.

The input side (virtual pointer, touch injector) exists purely so an automated
test can *start* and *move* a drag with authentic serials on a headless seat.

### `wlr` crate additions (one additive 0.20.16 release)

- `Runtime::create_virtual_pointer_manager(&Display) -> Result<()>` — creates
  `wlr_virtual_pointer_manager_v1` (mirrors `create_virtual_keyboard_manager`).
- Internal `on_new_virtual_pointer` handler: attach the injected
  `wlr_pointer`/`wlr_input_device` to the seat and cursor exactly as
  `on_new_input`'s pointer branch does (record it, update capabilities,
  register motion/button listeners), reusing `on_input_destroy` for teardown —
  the pointer analogue of M4.1's `on_new_virtual_keyboard`.
- DnD wiring in `register_toplevel_and_input`: listen for the seat's
  `request_start_drag` and `start_drag` (both gated on `runtime.seat_ptr()`,
  null liveness — seat is display-owned):
  - `on_request_start_drag`: validate `event.serial` for the requesting
    seat-client; on success call the appropriate
    `wlr_seat_start_pointer_drag`/`start_touch_drag`. wlroots emits `start_drag`
    only on success.
  - `on_start_drag`: if the `wlr_drag` has an icon
    (`(*drag).icon` non-null), create a `wlr_scene_drag_icon` node parented in
    the overlay band so it renders above everything and follows the input.
- `Runtime::inject_touch_down/motion/up(...)` — **test-only** (`for_test`-style
  gating): synthesize a touch point through `wlr_seat_touch_notify_*` so a test
  can drive a touch drag with no touch protocol. Additive; no production caller.

### Compositor additions

- `compositor/src/lib.rs`: `create_virtual_pointer_manager(&display)` at boot,
  non-fatal (matching the decoration/layer/selection/virtual-keyboard blocks).
- `state.rs`: expected near-zero — drag routing and the icon node live in the
  crate; the compositor already drives pointer focus. Any change is limited to
  ensuring the drag icon's position updates ride the existing pointer-motion
  path (if wlroots' scene drag icon does not self-track).

## Testing (automated-only)

- **Wire-level (extend `harness` + `compositor/tests/client_protocol.rs`):**
  - *Pointer drag round-trip*: client A maps + binds `wl_data_device`; a
    `VirtualPointerClient` (new `zwp_virtual_pointer_v1` harness client) injects
    a button press (minting a grab serial the compositor delivers to A), A calls
    `start_drag` with a `text/plain` source; the virtual pointer moves over B;
    a button release drops; B receives `wl_data_device.data_offer` +
    `enter`/`drop`, `receive()`s the fd, and the harness asserts the bytes.
  - *Touch drag round-trip*: same shape, driven by the crate's `inject_touch_*`
    against a focused destination.
  - *Negative*: a `start_drag` with a serial the client never received is
    refused (no drag begins; the destination gets no offer).
- **`wlr` crate unit tests:** `create_virtual_pointer_manager` double-create
  guard; grab-serial validation accept/reject (deletion-verified).
- **Gates:** `cargo test --workspace` + `cargo clippy --all-targets -- -D
  warnings` (icedtea); `cargo test -p wlr` + clippy + `RUSTDOCFLAGS="-D
  warnings" cargo doc -p wlr --no-deps` (wlroots-sys) — green on the freeze
  commit before publish.

## Success criteria

1. A pointer-driven drag from one client transfers a `text/plain` payload to a
   second client on drop, asserted at the byte level by an automated test.
2. A touch-driven drag does the same, via the crate's touch injector.
3. A drag whose `start_drag` serial is invalid is refused (negative test).
4. The drag icon renders as a scene node following the input (asserted via the
   model/scene where observable, else covered by the manual VM note).
5. `create_virtual_pointer_manager` and the DnD wiring are semver-additive,
   published as one `0.20.x` release; the compositor consumes the published
   crate.
6. All gates green in both repos; final whole-branch review clean or resolved;
   merge window presented.

## Out of scope (explicit)

- Tablet/pen DnD (`wlr_tablet` drags).
- Cross-`wl_data_device`/primary interactions beyond what M4.1 shipped.
- Compositor-initiated drags, drag-and-drop *to* the compositor's own surfaces
  (there are none — the shell's panel is not a drop target in v1).
- A general virtual-touch *protocol* — touch injection is a test-only crate
  helper, not a published Wayland global.

## Risks

- **Drag-icon self-tracking.** If wlroots' `wlr_scene_drag_icon` does not move
  the icon with the input automatically, the compositor must update its
  position on pointer/touch motion. Mitigation: the pointer-drag test asserts
  the icon node exists and moves; if manual positioning is needed it is a
  localized addition on the existing motion path.
- **Grab-serial availability headlessly.** Resolved by the virtual pointer
  (mints a real button serial) and the touch injector (mints a touch serial) —
  the same resolution M4.1 used for the keyboard serial. If wlroots requires
  the *pointer to be over a surface* to deliver the serial, the test maps the
  source client under the injected pointer first.
- **Virtual-pointer/keyboard lifecycle overlap.** The virtual-pointer attach
  reuses `on_input_destroy` and the `InputDevice` drop-order fix from M4.1;
  the same soundness applies. A review checklist item confirms no new
  drop-order hazard.
