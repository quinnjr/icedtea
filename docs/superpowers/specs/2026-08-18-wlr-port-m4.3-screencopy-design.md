# icedtea-wm — wlr port Milestone 4.3: Screencopy (output capture)

Date: 2026-08-18

## Overview

M4.3 exposes `zwlr_screencopy_manager_v1` so clients can capture an output's
rendered contents — the protocol screenshot tools (grim, wf-recorder) and the
screen-sharing portal (xdg-desktop-portal-wlr) use today. wlroots implements
the **entire** capture flow internally: buffer-geometry negotiation, the copy
from the output's rendered buffer, damage, and the `ready`/`failed` result.
The compositor wires **no events** — it only creates the global at boot, the
same one-call additive pattern M4.1's selection managers used. The substance
of the milestone is a headless capture client in the harness and a
non-vacuous pixel assertion that the captured bytes are the output's real
composited content.

## Decisions of record

1. **Scope: `zwlr_screencopy_manager_v1` only** — output capture over the
   `wl_shm` path. The newer `ext-image-copy-capture` family
   (`ext_image_copy_capture_manager_v1` + `ext_output_image_capture_source_manager_v1`
   + foreign-toplevel source) is explicitly deferred: `zwlr_screencopy` is
   what current tooling and the screen-share portal bind, and it is a single
   additive global. (User decision, 2026-08-18.)
2. **The `wlr` crate wraps wlroots' screencopy manager.** No protocol from
   scratch: `wlr_screencopy_manager_v1_create(display)` is the whole server
   side. No `capture_output` handler, no frame events, no teardown listener —
   the manager is display-owned and lives for the display's lifetime, exactly
   like `create_primary_selection_manager`.
3. **The `wl_shm` capture path is what we prove.** wlroots supports both
   `wl_shm` and linux-dmabuf capture buffers automatically once the manager
   exists; the automated test drives the `wl_shm` path (dmabuf capture needs
   GPU-allocated buffers a headless test cannot easily produce). Exposing the
   manager gives real consumers both paths regardless.
4. **Testing is automated, via a headless capture client.** A new harness
   `ScreencopyClient` binds the manager + `wl_output`, requests a capture,
   honours the buffer geometry/format wlroots advertises, and reads the
   pixels back. The load-bearing assertion is against the output's known
   background color (a solid `render::wallpaper_color` rect fills the scene).
5. **Split-phase publish → consume, as in M1–M4.2.** One additive `wlr`
   `0.20.x` release (**0.20.19**) carries `create_screencopy_manager`; the
   API-review verdict is held before the mechanical publish; the compositor
   then bumps and consumes. Additive-only within 0.20.x.
6. **Execution: inline or SDD (user's choice at plan handoff).** Per-task
   review, final whole-branch review, merge window presented — never
   auto-merged.

## Architecture

wlroots owns the capture state machine. When a client calls
`zwlr_screencopy_manager_v1.capture_output`, wlroots creates a
`zwlr_screencopy_frame_v1`, sends the client the required buffer size, format,
and stride, waits for the client to attach a buffer and call `copy`, blits the
output's most-recent rendered contents into it, sends `flags` then `ready`
(or `failed`). None of this is compositor-visible: the only server-side
requirement is that the manager global exists and the output renders frames.

The compositor already drives the scene: `wlr_scene_output_commit` runs on the
output frame handler, and the boot scene contains a background rect of
`render::wallpaper_color(&config.appearance)` filling the output. Screencopy
schedules an output frame if none is pending, so a capture reflects that
committed scene.

### `wlr` crate additions (one additive 0.20.19 release)

- `RuntimeInner.screencopy_manager: RefCell<Option<NonNull<sys::wlr_screencopy_manager_v1>>>`
  (init `None`), alongside the existing manager fields.
- `Runtime::create_screencopy_manager(&self, display: &Display) -> Result<()>`
  — a byte-for-byte structural mirror of `create_primary_selection_manager`:
  double-create guard returning
  `Error::Operation("Runtime::create_screencopy_manager called twice")`;
  `unsafe { sys::wlr_screencopy_manager_v1_create(display.as_ptr()) }`;
  `NonNull::new(...).ok_or(Error::Create("wlr_screencopy_manager_v1_create"))?`;
  store into the cell; `Ok(())`. No handler, no listener.
- Unit test (deletion-verified): first call stores `Some`, second call returns
  the double-create `Error::Operation`.

### Compositor additions

- `compositor/src/lib.rs`: a `create_screencopy_manager(&display)` block at
  boot, non-fatal (logs and continues on `Err`), placed beside the existing
  `create_virtual_pointer_manager` block (~line 100).
- `state.rs`: no change expected — screencopy has no routing and no
  compositor-visible surface.

### Harness additions

- `wl_output` binding in the harness registry (not currently bound): capture
  needs the `wl_output` object to pass to `capture_output`.
- `ScreencopyClient` (new, in `harness/src/lib.rs`): binds
  `zwlr_screencopy_manager_v1` (from `wayland-protocols-wlr`, already a dep —
  no new crate) and `wl_output`; calls
  `capture_output(overlay_cursor = 0, output)`; drives the
  `zwlr_screencopy_frame_v1` lifecycle:
  - `buffer(format, width, height, stride)` → allocate a `wl_shm` buffer of
    that exact geometry/format using the harness's existing shm machinery;
  - `buffer_done` → `frame.copy(buffer)`;
  - `flags`, then `ready` (success) or `failed`;
  - on `ready`, mmap the pool and expose the pixels.
  - Public accessor, e.g. `capture_output() -> CapturedFrame { width, height,
    format, stride, bytes }`.

## Testing (automated-only)

Extend `harness` + `compositor/tests/client_protocol.rs`:

1. **Global advertised.** `zwlr_screencopy_manager_v1` appears in
   `advertised_globals` (mirrors `virtual_pointer_manager_global_is_advertised`).
2. **Empty-output capture is the wallpaper color (load-bearing).** Boot the
   compositor; `ScreencopyClient` captures the output; assert the returned
   buffer is the output's size, that **every pixel is identical** (a cleared
   or garbage buffer fails this), and that that uniform color equals
   `render::wallpaper_color` mapped through the format wlroots reported, within
   a small per-channel tolerance (±2) to absorb any renderer color-space /
   rounding difference. Expected bytes are derived through the *same*
   rgba→reported-format conversion, so byte order cannot make the test vacuous.
3. **Capture reflects a mapped toplevel.** Map a toplevel backed by a known
   solid color at a known position; capture; assert the pixels inside the
   toplevel's region show that color (differing from the wallpaper),
   demonstrating the capture reflects real composited content rather than a
   background clear. Fallback if exact coordinates prove fragile: assert the
   capture is **not** uniform and contains the toplevel color somewhere.

**Gates:** `cargo test --workspace` + `cargo clippy --all-targets -- -D warnings`
(icedtea); `cargo test -p wlr` + clippy + `RUSTDOCFLAGS="-D warnings" cargo doc
-p wlr --no-deps` + `cargo fmt --all --check` (wlroots-sys — the fmt gate that
PR #3's CI enforces) — all green on the freeze commit before publish.

## Success criteria

1. `zwlr_screencopy_manager_v1` is advertised to clients (automated test).
2. An automated screencopy client captures the headless output and reads back
   a full-size `wl_shm` buffer whose pixels are uniform and equal the
   configured wallpaper color within tolerance — a non-vacuous pixel assertion
   proving the capture is the output's real rendered content.
3. A capture taken with a mapped toplevel reflects the toplevel's content in
   the output (proves composited pixels, not a background clear); fallback
   assertion documented if exact placement is fragile.
4. `create_screencopy_manager` is semver-additive, published as one `0.20.x`
   release (0.20.19); the compositor consumes the published crate.
5. All gates green in both repos; final whole-branch review clean or resolved;
   merge window presented for the user's go/no-go — never auto-merged.

## Out of scope (explicit)

- The `ext-image-copy-capture` family (`ext_image_copy_capture_manager_v1`,
  `ext_output_image_capture_source_manager_v1`, foreign-toplevel image
  source). Deferred; a later milestone if newer tooling requires it.
- linux-dmabuf capture-buffer assertions and region-capture assertions
  (wlroots supports both automatically once the manager exists; the automated
  test proves the `wl_shm` full-output path).
- Cursor overlay in the capture (`capture_output` `overlay_cursor` flag; the
  v1 test passes `0`).
- Screen recording / continuous capture / damage-tracking assertions.
- xdg-desktop-portal-wlr wiring — the protocol is exposed; portal
  configuration is system integration, not compositor code.

## Risks

- **Headless rendering.** The one genuine unknown: the headless output must
  render a frame containing the scene for the copy to have real content.
  Mitigation: the harness runs the production event loop with the wallpaper
  rect in the scene, and screencopy forces an output frame; criterion 2 is
  self-diagnosing — a black/cleared readback where the wallpaper color was
  expected *is* the finding, surfaced immediately by the first capture test
  rather than hidden. (A capture client spike was offered as a pre-plan
  de-risk and declined; criterion 2 serves the same function as the plan's
  first deliverable.)
- **Buffer format / stride / color mapping.** The client must honour the
  advertised `format`/`stride` and the expected color must be derived through
  the reported format's byte order (see `buffer.rs`'s MSB-name/LSB-byte note).
  Mitigation: read geometry from the `buffer` event, never assume; assert
  uniformity plus tolerance rather than exact bytes.
- **`wl_shm` vs dmabuf negotiation.** wlroots may advertise a dmabuf-capable
  path; the client requests a `wl_shm` buffer (screencopy always supports it).
  Mitigation: allocate `wl_shm` explicitly for the format wlroots reports.
